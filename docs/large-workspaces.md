# rustd against cargo on larger workspaces and wider edits

The table in the README is one line added to one function in small projects, where cargo
alone already rebuilds in under a second. This file is the same comparison on bigger
workspaces and on edits that are not cargo's best case: a body deep in the dependency
graph, bodies changed in many crates at once, a signature change with its callers, a
generic function, a new function, a new type, a changed struct field, and `cargo test`.

Every row is the same edit on the same source, built by cargo alone and by rustd, in
wall-clock seconds, as `median (least–most)` of 5 runs unless the row says fewer. The
ratio is cargo's median divided by rustd's: over 1× rustd is faster, under 1× it is
slower. Rows where rustd is slower, or where it handed the build to cargo, are all here,
and are collected in [one table](#every-row-where-rustd-lost-or-cargo-did-the-build).

Measured at rustd `a235afe8091c047aea93d1fe1d916d8b86c9916d` with `harness/bench.py --shapes`.
The raw results are in `harness/results-large/*.json`; the tables below the summary are
printed from them by `bench.py --tables` and are not edited by hand.

## What was compared

- **cargo alone**: `cargo +1.99.0 build` (or `test`) with no rustd anywhere. No wrapper,
  the default dev profile, `CARGO_INCREMENTAL` and `RUSTFLAGS` unset so incremental
  compilation is on as cargo ships it, its own target directory (`target-ref`), and a
  finished build of the same tree before anything is timed. The linker is the one rustc
  1.99.0 uses by default on this target, the `rust-lld` it ships, which is also what
  rustd's side links with.
- **`cargo rustd`**: `cargo rustd build` after a first build and after the daemon has
  said the workspace is `ready`.
- **plain cargo after `rustd enable`**: `cargo build` with rustd turned on as cargo's
  rustc wrapper. This was measured in a separate run, so it has its own cargo-alone
  column next to it; compare it with that one.
- **cargo with mold**: cargo alone with `-C linker=clang -C link-arg=-fuse-ld=mold`
  (mold 2.40.4), for someone who has already tuned their setup. It was measured in the
  `cargo rustd` runs on Cranelift only.

Each run makes the edit, builds with every side, then takes the edit back and builds
again. The headline columns are the builds after the edit was made; the builds after it
was taken back are in the second table of each workspace. After each `cargo rustd`
build the program was run (or the tests' results read) and compared with cargo's for
the same source. No row differed.

The edits, by the name the tables use:

| name | generated workspaces | real projects |
|---|---|---|
| body, in the program's crate | a constant in `app/src/main.rs` | a line added to a function of the binary |
| body, in a library deep in the graph | a constant in `g000`, which every crate depends on | a line added to a function in a low library (nushell `nu-path`, cargo `cargo-util`, ripgrep `grep-matcher`) |
| bodies in N crates | one body in each of N libraries spread over the layers | one body in each of N workspace crates, where the project has that many the harness can edit |
| signature | a parameter added to `g000::mix` and to every call of it in every crate | a parameter added to one function and to its callers |
| generic function | the body of `g000::fold_all<T: Scale>`, used at the types of every crate | the body of a generic function |
| new function, new type | added to a library in the middle layer and used from its `lib.rs` | added to the deep library and used from the edited function |
| changed struct field | a field added to a struct of the middle library and to its constructors and users | nushell only |
| `cargo test -p` | the tests of `app` and of the middle library after a body edit | the tests of the deep library after a body edit |

## Machine

8 logical CPUs (Intel Xeon, a cloud VM that reports no model), 32.9 GB of RAM, a 124 GB
virtual disk, Linux 6.8.0-1060-aws, rustc 1.99.0 (b940084d7 2026-09-28), LLVM 20 for
the LLVM rows. The measurements were run one at a time with nothing else started on the machine; see
[Not verified](#not-verified) for what that does not rule out.

## Summary

Cranelift, `cargo rustd`, cargo alone as described above. Seconds, median of 5.

| workspace | edit | cargo alone | rustd | cargo ÷ rustd | cargo with mold |
|---|---|---|---|---|---|
| gen200 | body, in the program's crate | 2.07 | 0.48 | 4.3× | 1.60 |
| gen200 | body, in a library deep in the graph | 8.01 | 2.79 | 2.9× | 7.84 |
| gen200 | bodies in 30 crates | 6.11 | 2.40 | 2.5× | 5.98 |
| gen200 | generic function used at many types | 6.14 | 3.92 | 1.6× | 5.96 |
| gen200 | signature, callers updated in every crate | 12.58 | 15.18 | 0.8× | 12.45 |
| gen200 | new function | 1.93 | 3.19 | 0.6× | 1.74 |
| gen50 | body, in a library deep in the graph | 1.32 | 0.57 | 2.3× | 1.28 |
| gen50 | bodies in 30 crates | 1.47 | 0.66 | 2.2× | 1.40 |
| nushell | body, in the program's crate | 1.91 | 1.17 | 1.6× | 1.70 |
| nushell | body, in a second deep library (`nu-utils`) | 5.99 | 3.28 | 1.8× | 5.82 |
| nushell | bodies in 10 crates | 6.57 | 3.35 | 2.0× | 6.33 |
| nushell | body in `nu-path` (cargo did the build) | 11.10 | 78.07 | 0.1× | 8.91 |
| cargo | body, in the program's crate | 4.99 | 2.27 | 2.2× | 4.93 |
| cargo | bodies in 3 crates | 6.74 | 2.60 | 2.6× | 6.62 |
| cargo | signature (cargo did the build) | 10.32 | 129.04 | 0.1× | 9.59 |
| ripgrep | new function | 1.35 | 0.59 | 2.3× | 1.24 |
| any | `cargo test -p` a library, with its doctests | 0.25–0.71 | 3.8–20.8 | under 0.1× | 0.24–0.73 |

What the numbers say:

1. When the daemon does the build, a body edit is 1.6× to 4.3× faster than cargo, and
   the gap grows with how much of the workspace cargo has to recompile. Changing bodies
   in 3, 10 or 30 crates costs rustd about the same as changing one deep body, so
   scattered edits are 1.6× to 2.7×. These are larger absolute savings than the README's
   table (seconds, not tenths) but not larger ratios.
2. mold changes little here. The cargo-with-mold column is within about 15% of cargo
   alone on nearly every row and at best 1.3× faster (gen200, body in the program's
   crate); cargo's time on these edits is mostly rustc, not the link.
3. A signature change that reaches every crate is slower under rustd than under cargo
   on the generated workspaces at 50 and 200 crates (0.9× and 0.8×). At 200 crates a
   new function, a new type and a changed field are slower too (0.6× to 0.9×); at 10
   and 50 crates they are faster (1.3× to 2.6×).
4. `cargo test -p <library>` after an edit is 8 to 34 times slower under `cargo rustd`
   than under cargo in every workspace, although the daemon's own steps for the
   test executable add up to well under a second. The same command with `--lib` is 1.1× to 2.6× faster than
   cargo. The difference between the two commands is the doctest pass, so that is where
   the time goes; this was not traced further.
5. When the daemon hands a build to cargo it costs far more than cargo alone: 70 to
   130 s against 9 to 12 s on nushell and cargo. That happened for every edit to
   nushell's `nu-path/src/components.rs` and for nushell's signature edit (``` `eq` has
   errors ... frontend: mir: HasErrors ```), and for cargo's signature edit (`unsupported:
   writable static SOURCE_ID_CACHE without a rustc symbol`). The builds were correct.
   The slow rows were stopped after 3 or 4 runs instead of 5 to bound the time; the
   runs column says which.
6. Plain `cargo build` after `rustd enable` gains much less than `cargo rustd`. On an
   edit in the program's own crate it is 1.1× to 3.1× faster than cargo. On an edit deep
   in the graph or scattered over crates it is 1.0× to 1.6×, and on the generated
   signature edit it is 0.5× to 0.6×.
7. The LLVM backend, measured on gen50 and on a subset of nushell, is close to
   Cranelift on most rows, with the same losses and two differences: the generic edit on
   gen50 gains 1.3× instead of 2.3×, and a body in nushell's program crate is slower than
   cargo (0.8×) where Cranelift is faster (1.6×).
8. Memory and warm-up are the price. After the first build the daemon needs 11 s
   (gen10, ripgrep) to 203 s (gen200) before it builds anything, and it peaks at 2 GB
   (gen10), 6.3 GB (gen50), 15 to 16 GB (nushell, cargo) and 21.7 GB (gen200). In plain
   mode gen200's `target` directory grew past 72 GB.

## A whole session

A clean first build and then 20 edits one after another with no pause, in a fresh
checkout: under cargo alone, under rustd with the edits beginning the moment the first
build ends, and under rustd with the edits beginning when the daemon is ready (the wait
is counted). Cranelift, one session each, so these are single runs and not medians.

| workspace | cargo alone, total s | rustd, edits at once, total s | rustd, edits when ready: first build + wait + edits = total s | edits the daemon built | edits needed to pay back the wait |
|---|---|---|---|---|---|
| gen10 | 11.7 | 21.1 | 2.0 + 11.4 + 6.8 = 20.2 | 20 of 20 | about 75 |
| gen50 | 38.9 | 63.9 | 7.5 + 41.8 + 24.7 = 74.0 | 20 of 20 | about 120 |
| gen200 | 157.1 | 261.0 | 27.9 + 164.3 + 113.6 = 305.8 | 20 of 20 | about 210 |
| ripgrep | 22.0 | 38.4 | 5.9 + 12.0 + 9.2 = 27.0 | 20 of 20 | about 35 |
| nushell, edits the daemon builds | 182.1 | not run | 47.6 + 200.0 + 72.7 = 320.3 | 20 of 20 | about 65 |
| nushell | 161.5 | 262.7 | 40.6 + 187.7 + 207.3 = 435.6 | 1 of 20 | never |
| cargo | 177.4 | 266.8 | 45.3 + 120.3 + 290.5 = 456.2 | 4 of 20 | never |
| rust-analyzer (not loaded) | 252.1 | 420.9 | 52.1 + 370.4 + 341.0 = 763.6 | 0 of 20 | never |
| helix (not loaded) | 147.1 | 217.5 | 35.6 + 211.5 + 171.9 = 419.0 | 0 of 20 | never |

No 20-edit session was faster under rustd than under cargo. Where the daemon built every
edit, the edits themselves took 0.5 to 0.9 of cargo's time, and the warm-up is paid back
after roughly the number of edits in the last column (the wait divided by what an
average edit of that session saves).

Three things in this table are losses worth knowing about:

- Edits made while the daemon is still loading are built by cargo and take 1.6 to 2
  times as long as under cargo alone, presumably because the load is using the same
  CPUs.
- After a build the daemon hands to cargo, it loads again, and the edits that follow
  are handed to cargo too (`the daemon is still loading the workspace`). In the nushell
  and cargo sessions one unsupported edit near the start cost most of the session.
  The row "nushell, edits the daemon builds" is the same session with the two edits the
  daemon hands over replaced by ones it builds (`leaf2` and bodies in 10 crates); it is
  there to show both cases, not to replace the other row.
- The edit sequence includes the signature change, which is a loss on gen50 and gen200.

## Not verified

- The machine is a shared cloud VM. Some rows have a wide spread (the range is printed
  next to each median); the nushell rows built by cargo in particular vary from 14 to
  99 s.
- The plain-cargo runs and the `cargo rustd` runs were made at different times, and
  cargo alone was up to twice as slow in some plain-cargo runs (gen10 and gen50) as in
  the `cargo rustd` runs. Each ratio uses the cargo-alone time of its own run.
- gen200 in plain mode stopped when the disk filled: bodies in 30 crates, signature,
  generic, new function, new type, field and the tests have no plain-mode number.
- Plain mode on nushell and cargo, and LLVM on nushell, were run on a subset of the
  edits (no signature, new function, new type or field on nushell; no signature on
  cargo). LLVM was not run on gen10, gen200, cargo or ripgrep. mold was not measured
  against LLVM or plain mode.
- Real projects have no "bodies in 30 crates" row, and cargo and ripgrep have no 10-crate
  row, because the harness did not find that many crates it could edit. Only nushell has
  a struct-field row. No real project has a `cargo test` of the binary's crate.
- `cargo test -p app` on the generated workspaces was built by cargo, because the
  daemon could not load a test that uses `env!("CARGO_BIN_EXE_app")`.
- Why the handed-over builds take 70 to 130 s, why `cargo test` with doctests is slow,
  and why edits during loading are slower than cargo alone were not investigated; the
  explanations above are guesses from the timings.
- Sessions were run once each. Whether a restarted daemon loads faster from its cache
  than the first load measured here was not measured.
- The README gives 42 s for the daemon to load nushell after the first build. Here it
  took 171 s (Cranelift, 142 s of it compiling) in a fresh daemon home, and 188 to 200 s
  in the sessions. I did not find out why the two differ.
- Only Linux x86-64.

## How to reproduce

```sh
rustup toolchain install 1.99.0 --component rust-src
cargo +1.99.0 build -p rustd --release                 # Cranelift
# LLVM rows: build with --features llvm as the README says
export RUSTD_BENCH_MOLD=/path/to/mold                   # optional, adds the mold column
cd harness
python3 bench.py --shapes gen10 gen50 gen200 --session 20 --out results-large/generated.json
python3 bench.py --shapes gen10 gen50 --mode plain      --out results-large/generated.json
python3 bench.py --shapes gen50 --backend llvm          --out results-large/generated.json
python3 bench.py --shapes nushell --session 20          --out results-large/nushell.json
python3 bench.py --shapes nushell --only session --session 20 --think ready \
    --session-shapes body --session-shapes leaf2 --session-shapes scatter3 \
    --session-shapes generic --session-shapes scatter10 --out results-large/nushell-session-supported.json
python3 bench.py --shapes cargo --session 20            --out results-large/cargo.json
python3 bench.py --shapes ripgrep --session 20          --out results-large/ripgrep.json
python3 bench.py --tables results-large/*.json          # the tables below
python3 bench.py --tables --losses results-large/*.json # the table of losses
```

Add `--mode plain` for plain cargo after `rustd enable` and `--backend llvm` for LLVM;
those were run on ripgrep in full, and on nushell and cargo with the edits named under Not verified
left out by `--only`. `--runs N` sets the runs (5), `--only SHAPE` picks edits, `--work DIR` says where the
checkouts go. gen200 needs about 25 GB of RAM and, in plain mode, more than 90 GB of
disk. The whole set took about ten hours on this machine.
